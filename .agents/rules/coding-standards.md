# Project Coding Standards (มาตรฐานการเขียนโค้ด)

## 1. Security (ความปลอดภัยทั่วไป)
- **ห้ามฮาร์ดโค้ด (No Hardcoding):** ห้ามเก็บ Credentials, Secrets, หรือ Token ใดๆ ไว้ในซอร์สโค้ดโดยตรง ให้ดึงผ่าน Environment Variables (`process.env`) เสมอ
- **จัดการข้อมูลส่วนบุคคล:** ห้ามบันทึกรหัสผ่านหรือข้อมูลที่ละเอียดอ่อนลงฐานข้อมูลในรูปแบบ Plain-text ต้องทำการ Hash หรือเข้ารหัสก่อนเสมอ (เช่น ใช้ `bcryptjs` สำหรับรหัสผ่าน)
- **ตรวจสอบช่องโหว่:** หมั่นตรวจสอบช่องโหว่ของ Dependency ที่ใช้งาน (เช่นใช้คำสั่ง `npm audit`)

## 2. API Security (ความปลอดภัยของ API)
- **Validate Input เสมอ:** ข้อมูลทั้งหมดที่ส่งเข้ามายัง API (Body, Params, Queries) ต้องผ่านการ Validate อย่างเข้มงวดด้วย `Zod` ห้ามเชื่อถือข้อมูลจากฝั่ง Client เด็ดขาด
- **SQL Injection Prevention:** ใช้ `Drizzle ORM` ในการจัดการฐานข้อมูลเสมอ หลีกเลี่ยงการต่อสตริง (String Concatenation) เพื่อสร้างคำสั่ง SQL ดิบๆ โดยตรง
- **ซ่อนรายละเอียด Error (Data Leakage):** ห้ามส่ง Stack Trace หรือข้อความ Error เชิงลึกของ Database กลับไปให้ผู้ใช้งาน หากเกิด Error ร้ายแรงให้ส่งกลับเป็นเพียง "Internal server error" เท่านั้น (ผ่าน `errorResponse`)
- **การจัดการสิทธิ์ (Authorization):** ตรวจสอบสิทธิ์การเข้าถึงและการแก้ไขข้อมูลของ User เสมอ (เช่น ลบได้เฉพาะสินค้าของตนเอง หรือแอดมินเท่านั้น)

## 3. Clean Code & Reusable Code (โค้ดที่สะอาดและนำไปใช้ซ้ำได้)
- **แบ่งโครงสร้างชัดเจน (Separation of Concerns):** ห้ามเขียน Logic ยาวยืดในไฟล์ `route.ts` ให้กระจายโค้ดออกเป็น 3 ชั้น: `schema` (ข้อมูล), `service` (จัดการ Logic), และ `repository` (ติดต่อฐานข้อมูล)
- **DRY (Don't Repeat Yourself):** หากมี Logic ที่ใช้งานซ้ำหลายที่ ให้แยก (Extract) ออกมาเป็น Utility Function แล้วนำไปเก็บไว้ใน `src/lib/`
- **Single Responsibility Principle:** ฟังก์ชันหนึ่งฟังก์ชันควรทำงานเพียงแค่อย่างเดียวเท่านั้น หากฟังก์ชันยาวเกินไป ให้ซอยย่อยเป็นฟังก์ชันเล็กๆ
- **ตั้งชื่อให้สื่อความหมาย:** ชื่อตัวแปรและฟังก์ชันควรชัดเจนว่าเก็บค่าอะไรหรือทำหน้าที่อะไร และห้ามใช้ Type `any` เด็ดขาด เพื่อลดข้อผิดพลาด

## 4. Code Commenting (การคอมเมนต์โค้ด)
- **คอมเมนต์เป็นภาษาไทย:** คำอธิบายโค้ด (Comments) และ JSDoc ให้เขียนเป็น **ภาษาไทย** ทั้งหมด เพื่อให้โปรแกรมเมอร์ในทีมเข้าใจบริบทได้ง่ายที่สุด
- **เน้นอธิบายเหตุผล (Why):** ไม่ต้องคอมเมนต์แปลว่าโค้ดทำอะไร (เพราะโค้ดที่ Clean จะอ่านออกอยู่แล้ว) แต่ให้เน้นคอมเมนต์เพื่อบอก **"เหตุผล"** ว่าทำไมถึงต้องเขียนด้วยวิธีนี้ หรืออธิบาย Business Logic ที่ซับซ้อน
- **เขียน JSDoc สำหรับ Utility:** ฟังก์ชันใน `lib` หรือ `service` ที่สำคัญ ให้ใช้ JSDoc อธิบายพารามิเตอร์และการรีเทิร์นค่า (ด้วยภาษาไทย)
